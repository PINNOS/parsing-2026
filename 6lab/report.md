# Отчёт по лабораторной работе №6

**Вариант 1. Товарный каталог**

## 1. Цель
Построить слой хранения и качества данных (raw → clean → mart): объединить минимум два источника разной природы (API + HTML/краулинг), реализовать очистку с протоколом, контракт данных через Pydantic, идемпотентную загрузку в SQLite с UPSERT, историю изменений, метрики качества со светофором, аналитические представления в mart и сопоставление с no-code реализацией.

## 2. Источники данных
Объединены два набора, собранных ранее:
- Лаб. 3 (REST API) — `3lab/data_raw.jsonl`
- Лаб. 5 (Scrapy/краулинг) — `5lab/lab5_6/data/items.jsonl`

Разная природа (JSON API vs HTML/Scrapy) объединены в единую общую схему товарного каталога (бизнес-ключ, название, цена, остаток, рейтинг, категория, источник).

## 3. Трёхслойное хранилище
- `raw/` — JSON Lines, **только дозапись**: файл открывается в режиме `open("a")`, никогда не удаляется и не перезаписывается, изменение существующих строк запрещено. Дозапись идемпотентна — запись, уже присутствующая в файле, повторно не добавляется, поэтому повторный прогон не создаёт дублей и не меняет ни одной существующей строки. Каждая запись содержит служебные поля `_source`, `_source_url`, `_collected_at`, `_parser_version`, `_status`.
- `clean/` — типизированные данные (Parquet), `rejects.jsonl` с причинами отбракования.
- `mart/` — агрегаты и партиционированные снапшоты по дате сбора.

Пересборка clean из raw реализована в `src/rebuild.py`.

## 4. Сравнение форматов (CSV/JSONL/Parquet)
Замеры выполнены в ноутбуке. Ключевые выводы: Parquet обеспечивает колоночное хранение, сжатие, сохранность типов (в т.ч. дат, строк с ведущим нулём и цены как `decimal128(12,2)`), чтение по подмножеству столбцов быстрее текстовых форматов. Для чистого слоя выбран Parquet, для сырого — JSONL, CSV — только для обмена.

## 5. Очистка
Применена последовательность: нормализация текста (NFKC, схлопывание пробелов), формирование бизнес-ключа (стабильный), типизация (целые с NULL, UTC-даты, **деньги — не `float`**: в контракте `Decimal`, в Parquet `decimal128(12,2)`, в БД целое число копеек), работа с пропусками (обязательные → отбраковка), дедупликация (по бизнес-ключу, оставлена самая свежая), бизнес-правила (≥5). Протокол шагов с числами (строк до/после, изменений) приведён в `6lab.ipynb`.

## 6. Контракт данных (Pydantic)
Модель `Product` с типами, ограничениями, ≥2 field_validator, проверками согласованности. Демонстрация на заведомо битых записях в ноутбуке. Невалидные попадают в `rejects.jsonl` с указанием причины.

## 7. БД, UPSERT, история, идемпотентность
Схема `db/schema.sql`, загрузка через UPSERT (ON CONFLICT DO UPDATE); деньги хранятся как `price_cents INTEGER` (минорные единицы — во `float` денежные значения не попадают), представление `products_v` отдаёт цену в рублях для чтения. Продемонстрированы три прогона: повтор с теми же данными не меняет `updated_at`, третий с изменением 2 записей обновляет только их, история изменений фиксирует изменения. Работа ограничений (CHECK/PRIMARY KEY) показана.

## 8. Метрики качества и «светофор»
Рассчитаны 7 метрик (полнота обязательных и необязательных полей, уникальность ключа, валидность, доля отбраковки, согласованность правил, возраст загрузки) с обоснованными порогами зелёный/жёлтый/красный, выведен вердикт. При красном статусе загрузка в mart прерывается (реализовано в `src/quality.py` и функцией `assert_green` в ноутбуке).

## 9. Слой mart
Созданы ≥3 аналитических представления (агрегаты по категории, по ценовым диапазонам, топ-N), партиционирование снапшотов по дате сбора, демонстрация чтения одной партиции, графики распределений.

## 10. No-code часть и сопоставление «код vs no-code»

### 10.1. Workflow

`nocode/workflow.json` — 7 узлов n8n (импортирован в локальный инстанс, id `P15hsqGnxJdddXmI`):

| Узел | Тип | Назначение |
|---|---|---|
| Schedule Trigger | `scheduleTrigger` | расписание: ежедневно, 06:00 (Europe/Moscow) |
| Load Clean Subset | `code` | 43 входа: 40 валидных записей + 1 дубль ключа + 2 заведомо невалидные |
| Normalize Fields | `code` | нормализация: NFKC, схлопывание пробелов, приведение чисел и булевых |
| Remove Duplicates | `removeDuplicates` | дедупликация по `product_key` |
| Valid? | `if` | `title` не пуст И `product_key` не пуст И `price > 0` |
| Upsert Products | `postgres`, `upsert` | UPSERT по `product_key` (ветка «валидно») |
| Rejects Table | `postgres`, `insert` | отбраковка с причиной (ветка «невалидно») |

**Результат прогона** (PostgreSQL 16, схема `db/schema_pg.sql`, таблицы `products`/`rejects`):

| Показатель | Значение |
|---|---|
| Вход | 43 |
| После дедупликации | 42 |
| Загружено (UPSERT) | **40** |
| Отбраковано (rejects) | **2** (`bad_1` — пустой `title`, `bad_2` — `price <= 0`) |
| Дубль `c_1` | отсечён дедупликацией (в БД цена 11.00, а не 999.00 из дубля) |

Выгрузка результата: `nocode/nocode_result.csv` (40 строк), `nocode/nocode_rejects.csv` (2 строки), скриншот — `nocode/screen_run.png`.

### 10.2. Таблица сопоставления

| Этап | Код (`6lab.ipynb`) | No-code (n8n) | Нереализуемо / ограничение |
|---|---|---|---|
| Нормализация текста (NFKC, пробелы) | `norm_text` через `unicodedata` | Code-узел `Normalize Fields` | — |
| Бизнес-ключ | `make_key` (UPC/слаг, не URL) | — | n8n не строит ключ из HTML-полей без Code-узла; ключ подаётся готовым |
| Типизация | `Decimal`, nullable-`Int64`, `datetime64[ns, UTC]` | Code-узел (`Number`, `Boolean`) | n8n не хранит `Decimal`; точность денег обеспечивает тип колонки БД (`NUMERIC(12,2)` в PostgreSQL, `price_cents INTEGER` в SQLite) |
| Пропуски обязательных полей → отбраковка | маска + `rejects.jsonl` | узел `Valid?` → `Rejects Table` | — |
| Дедупликация по бизнес-ключу | `drop_duplicates(keep="last")` по свежести сбора | `Remove Duplicates` (`product_key`, keep first) | **ограничение:** в коде побеждает самая свежая запись, в n8n — первая; выбора по времени у узла нет |
| Бизнес-правила (≥5) | 5 правил (цена > 0 и < 10000, рейтинг 1..5, остаток ≥ 0, нет конфликта «в наличии при остатке 0») | 3 условия в `Valid?` | **ограничение:** диапазон цены, `stock >= 0` и конфликт «в наличии при остатке 0» в n8n не проверяются |
| Контракт данных (Pydantic: 3 `field_validator` + 1 `model_validator`) | `src/contract.py` / ячейка ноутбука | — | **нереализуемо:** в n8n нет декларативной схемы записи; доступна только грубая проверка `If` |
| UPSERT в БД | SQLite `ON CONFLICT DO UPDATE ... WHERE` (условное обновление) | Postgres-узел `upsert` по `matchingColumns` | **ограничение:** n8n всегда переписывает строку, поэтому `updated_at` не может меняться «только при реальном изменении», как в коде |
| История изменений | таблица `product_history` (снапшоты по прогонам) + запрос «состояние на дату» | — | **нереализуемо** в этом графе (потребовался бы отдельный `insert` в историю до `upsert`) |
| Метрики качества и «светофор» (7 метрик, прерывание при красном) | `src/quality.py` + `assert_green` | — | **нереализуемо:** у n8n нет порогов качества и агрегированного вердикта |
| Mart: 3 представления, партиционирование, графики | pandas / PyArrow | — | **нереализуемо:** n8n не выполняет аналитику и не строит графики |
| Расписание запуска | запуск вручную / по требованию | `Schedule Trigger` (ежедневно) | в коде нет планировщика — это плюс no-code |

### 10.3. Вывод

No-code уверенно закрывает «механическую» часть конвейера: расписание, нормализацию, дедупликацию, разделение валидных и невалидных записей и UPSERT по бизнес-ключу — то есть ту часть, где логика фиксирована и повторяема. Всё, что требует декларативного контракта, семантического сравнения версий записи, агрегированных метрик качества и аналитики, реализуемо только кодом. Итоговая рекомендация — гибрид: сбор и загрузка в n8n по расписанию, контроль качества и построение `mart` в коде.
