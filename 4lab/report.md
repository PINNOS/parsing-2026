# Лабораторная работа № 4. Сбор данных с динамических страниц: Playwright и no-code

**Вариант 6:** `scrapingcourse.com/button-click` (кнопка «Load more») + `books.toscrape.com` (пагинация).
**Версия документа:** 1.1 (2026-10-17). История изменений в конце документа.
**Статус:** код, наборы, замеры, сверка и no-code (n8n) готовы. Сценарий n8n прогнан, результат совпадает с браузерным набором по `load_more`, см. раздел 7.

## 1. Цель и вариант

Диагностировать источник, собрать ≥ 200 записей браузером (≥ 5 циклов взаимодействия), реализовать дешёвую альтернативу, сравнить по измерениям, оценить устойчивость и правовые риски.

Вариант 6 по условию — `scrapingcourse.com/button-click`, контрольный статический источник — `scrapingcourse.com/ecommerce`. Контрольный источник **не использован** по причине robots.txt (раздел 6).

## 2. Протокол диагностики источника

| Проверка | Результат |
|---|---|
| Ответ сервера (requests), `/button-click` | HTTP 200, `text/html`, 15 556 байт. Карточек `.product-name` в статическом HTML: **12** (первая порция), `li.product`: 0. Кнопка «Load more» есть |
| Поиск целевого текста в исходном HTML | Названия первых 12 товаров найдены прямо в HTML. JSON в `<script>` не найден (`__NEXT_DATA__`, `application/ld+json` отсутствуют). Обработчик кнопки — inline-скрипт с `fetch('/ajax/products?offset=…')` |
| Network / XHR (перехват `response` в Playwright) | Каждый клик: `GET /ajax/products?offset=N`, N = 10, 20, …; ответ — **HTML-фрагмент** (≈10 КБ, 12 карточек). На offset 140 — 7 карточек, на 150 — пустой ответ `204`, кнопка скрывается |
| Работа без JS | По статическому HTML доступны только первые 12 товаров, кнопка без JS не работает. Прямой прогон с `java_script_enabled=False` не делался, вывод сделан по HTML и коду обработчика |
| Вывод | Данные доступны через XHR-эндпоинт без браузера, поэтому браузер для **данных** формально не обязателен. Задание требует браузерный путь, поэтому реализованы оба: браузер (цикл «Load more» + замеры) и XHR через requests (дешёвая альтернатива, вариант B). Браузер нужен для **воспроизведения пользовательского сценария** и как эталон сверки |

Особенность: шаг `offset` = 10, а карточек в ответе 12. Соседние порции перекрываются на 2 товара, поэтому нужна дедупликация.

## 3. Схема реализации

**Браузерный путь (`collect_browser.py`):** `sync_playwright` → `browser → context → page` с `try/finally` и `browser.close()`. Контекст: `user_agent` (честный UA с контактом), `viewport 1280×900`, `locale ru-RU`, `set_default_timeout 15 с`, `set_default_navigation_timeout 30 с`.

- Раздел `load_more`: цикл клика по кнопке. Ожидание ответа через `expect_response` (`/ajax/products`), затем `wait_for_function`: прирост карточек **или** скрытие кнопки. `time.sleep(1)` — только пауза вежливости между циклами.
- Раздел `books`: цикл перехода по ссылке «next» (`expect_navigation`), 4 страницы.
- Предохранители: максимум циклов (30), остановка при `stall_limit = 2` циклах без прироста, лимит записей (400), максимум страниц. Конец каталога — скрытая кнопка или пустой ответ.
- Сбой ожидания (`TimeoutError`) — скриншот и HTML в `artifacts/`, ненулевой код возврата. Исключения не глушатся.
- Журнал: `collection_log.csv` (раздел, цикл, число элементов, прирост, длительность, timestamp, URL, HTTP-статус) и `logs/run_browser_*.jsonl`.

**Дешёвая альтернатива (`collect_light.py`):** requests + BeautifulSoup. `GET /ajax/products?offset=N` с шагом 10 (как `data-offset` на кнопке) и статическая пагинация `books` по ссылке «next». Повторы только для 429/5xx с экспоненциальной задержкой и full jitter, уважается `Retry-After` (секунды и дата). Сетевая ошибка (`ReadTimeout`) не повторяется, а останавливает источник с записью в журнал.

**Очистка:** бизнес-ключ — нормализованное название товара. Цена: `$`/`£` и разделители удаляются, остаётся число.

## 4. Таблица использованных локаторов и устойчивость

| Локатор | Тип | Обоснование | Риск при редизайне | Замена |
|---|---|---|---|---|
| `get_by_role("button", name="Load more")` | роль + текст | Не зависит от классов и обёрток | Смена текста на другой язык ломает поиск | `[data-testid="load-more-btn"]` (test-id есть в разметке) |
| `#product-grid .product-item` | id контейнера + семантический класс | id контейнера стабилен, потомки — через пробел (обёртки не важны) | Переименование класса карточки | Потомки `#product-grid` по признаку ссылки на товар |
| `.product-name`, `.product-price` | семантические классы, не сгенерированные | Не хэш-классы; читаются как «название» и «цена» | Переименование классов | `h2`/`[itemprop=name]` или атрибуты товара |
| `article.product_pod`, `h3 a` (атрибут `title`), `li.next a` / `get_by_role("link", name="next")` | тег + структура books.toscrape | Верстка стабильна много лет; `title` содержит полное название (текст ссылки обрезан) | Редизайн верстки каталога | — |

Структурный XPath и сгенерированные классы **не используются**. Оговорка: в JS-обработчике ожидания применяется id `#load-more-btn`. Его стоит заменить на `data-testid`, это на будущее.

**Сценарии редизайна:**
- переименование CSS-класса карточки: `load_more` даст 0 записей → smoke-check красный, цикл завершится по `stall`;
- добавление `div`-обёртки: локаторы потомков не сломаются;
- смена текста кнопки на другой язык: `get_by_role` перестанет находить кнопку, раздел закончится с `end_of_source` и **потеряет** записи без ошибки. Поэтому ожидается замена на test-id.

## 5. Сценарий взаимодействия, данные и замеры

**Итоговый набор: 227 уникальных записей** (147 из `load_more`, 80 из `books`), **19 циклов** взаимодействия (15 кликов «Load more» + 4 перехода «next»). Требования ≥ 200 записей и ≥ 5 циклов выполнены.

**Дедупликация:** сырых карточек 255, после дедупа 227. Потери: 28 из `load_more` (перекрытие порций, шаг 10 при 12 карточках), 0 в `books`.

**Почему не 200 с одного источника:** каталог `/button-click` содержит 147 уникальных товаров. Контрольный каталог `/ecommerce/` (≈188 позиций) по robots.txt недоступен, и в объединении с `load_more` даёт только 50 новых товаров (остальные — пересечение). Третий источник — `books.toscrape.com`, статический, разрешённый.

**Проверка качества (`smoke_check.py`, `quality_report.json`):**
- пустых полей `name`, `price`, `url`: 0 %;
- дубликатов по бизнес-ключу: 0;
- нечисловых цен: 0;
- вердикт: **green** для обоих наборов.

**Найденные дефекты, которые исправлены:**
- кодировка: `books.toscrape.com` не указывает charset, `requests` декодировал как ISO-8859-1 (`Shakespeareâ\x80\x99s`). Исправлено явным `utf-8`;
- двойные пробелы в названиях (`innerText` схлопывает, `get_text` нет) — нормализованы;
- цены `$52` и `$52.00` — приведены к числу;
- товары с разными URL (завершающий `/`, `--` в slug) — дедупликация по названию.

## 6. Правовая и этическая оценка

| Пункт | Значение |
|---|---|
| Площадки | Тренировочные: `scrapingcourse.com` (`/button-click`), `books.toscrape.com`. Коммерческих сайтов нет |
| robots.txt `scrapingcourse.com` | `User-agent: *`, `Disallow: /ecommerce/*`. Остальное разрешено (включая `/button-click` и `/ajax/products`) |
| robots.txt `books.toscrape.com` | 404 (файла нет), ограничений не задано |
| Нарушение | **Признаю:** до проверки robots.txt были запросы к `/ecommerce/` (диагностика и несколько прогонов браузера). Раздел исключён из набора, из замеров и из кода. Дальнейшие прогоны этот раздел не трогают |
| Защита и капча | На `/button-click` подключён скрипт Cloudflare Turnstile (`challenges.cloudflare.com/turnstile/v0/api.js`). С виджетом не взаимодействовали, челлендж не возникал, обхода не было |
| User-Agent | `StudentScraperBot/1.0 (+https://github.com/PINNOS/parsing)` во всех запросах (браузер и requests) |
| Нагрузка | 1 с пауза между циклами, таймаут 15 с, повторы только для 429/5xx, ≤ 30 циклов и ≤ 4 страниц |
| Персональные данные | Нет. Собраны названия товаров и книг, цены, URL и ссылки на изображения |
| Авторизация | Не используется (вариант без логина) |
| 152-ФЗ | ПДн не обрабатываются, основание не требуется. Данные хранятся локально, не публикуются |
| Контакт в UA | Указан репозиторий; для реальных проектов добавить e-mail владельца |

**Чего не хватает по процессу:** в скриптах нет автоматической проверки robots.txt перед запросом. Нарушение произошло из-за ручной проверки. Для следующих работ стоит добавить `urllib.robotparser` в клиент.

## 7. No-code реализация (n8n, прогнан)

`nocode/workflow.json` — сценарий n8n на основе найденного XHR-эндпоинта (рендер-API не нужен, JS-рендеринг не используется):

Manual/Schedule Trigger → Offsets (code, 15 значений offset) → HTTP Request (`/ajax/products`, пакетирование 1 элемент и пауза 1000 мс, 3 повтора, `continueErrorOutput`) → Extract Cards (htmlExtract) → Split Out → Extract Fields (htmlExtract: name, price, url, image) → Normalize (code: число из цены, пробелы, служебные поля) → Dedupe By Business Key (code) → Build CSV (code, бинарный файл) → Write CSV. Ветка ошибки HTTP → Error Branch (Set).

**Прогон (локальный n8n 2.43.7, контейнер `n8n-parsing-lab`):**
- исполнение `success`, 15.9 с, 15 HTTP-запросов;
- на выходе 175 карточек (совпадает с числом карточек браузера в DOM), после дедупа по бизнес-ключу **147 записей**;
- `nocode_result.csv` (147 строк, ≥ 20 требуется): сверка с браузерным `load_more`: совпадение 147/147, без лишних и пропущенных, пустых названий и цен нет.

**Что пришлось исправить по ходу:**
- `Execute Workflow Trigger` требует `inputSource: passthrough`;
- встроенный узел Remove Duplicates в этой версии не удалял дубли: заменён на Code-дедупликацию по бизнес-ключу;
- Convert to CSV возвращал 0 элементов без ошибки: заменён на Code, который строит CSV как бинарный файл;
- n8n разрешает файловые операции только в `~/.n8n-files`: путь записи выбран там, файл забран через `docker cp`. Путь через `./nocode` из `docker-compose.yml` в этом контейнере не смонтирован.

**Побочный эффект:** CLI-импорт создаёт новый workflow при каждом запуске, а не обновляет старый. В инстансе остались черновые копии `lab4_v6_scrapingcourse_button_click` (ids: `0kIVVxsLy3I96mUy`, `VYLxZesLctrGypiq`, `lQVgrVDwW9D452mm`, `WEGF5eNzDzTj7q4M`, `PIzErv8QZAuzTxKf`, `vbNWYBcEasoeyUJq`). Актуальная версия — `tEZArGupj0Prw6He`. Черновики стоит удалить в UI n8n.

**Не измерялось:** трафик и пиковая память для n8n (контейнер).

**Стоимость при масштабировании:** XHR-вариант не расходует JS-рендер, стоимость — число HTTP-запросов (15 на прогон). Для Playwright-сервисов рендеринга (ScrapingBee/Browserless) стоимость растёт пропорционально числу страниц и времени рендера. Оценка без проверки тарифов.

## 8. Выводы и рекомендации

1. **Разовое исследование:** XHR-эндпоинт через requests. Это 0.34 МБ трафика, 44 МБ памяти, 20 запросов. Браузер нужен, только если эндпоинт меняется, и для проверки.
2. **Ежедневный сбор 10 000 записей:** XHR-путь с пагинацией, расписание в n8n или cron, `state.json` с водяным знаком и ETag. Браузер не масштабируется: 977 МБ памяти на процесс и ≈0.13 с/запись (с паузами).
3. **Сайт под антибот-защитой:** не обходить. Проверить ToS и robots.txt, при запрете — остановить сбор и запросить доступ или API у владельца. Ротация прокси и подмена UA — не вариант.

**Ограничения данных:** выборка двух тренировочных площадок (227 записей), каждый режим измерен один раз, время разрозненно из-за пауз, трафик по `Content-Length` (для сжатых ответов может занижаться), каталог `load_more` содержит повторы из-за шага пагинации.
